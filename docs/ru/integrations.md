# Нативные интеграции

## Кроссплатформенная разработка
Ядро протокола OSTP (`ostp-core`) — `sans-io` и полностью независимо от платформы. Каждое хост-приложение линкует его и само предоставляет сеть, TUN-адаптер и UI — они описаны ниже.

## Мобильные платформы: приложение на Flutter + Android JNI-привязки
`ostp-flutter` — кроссплатформенное мобильное приложение (Flutter, сегодня — Android). На Android оно встраивает Rust-движок клиента через `ostp-jni`, отдельный крейт, экспортирующий небольшую C-ABI/JNI-поверхность (`Java_net_ostp_client_OstpClientSdk_*`: старт/стоп клиента, получение метрик, получение логов, добавление строки лога, уведомление о смене сети), которую использует Kotlin-слой приложения (`OstpClientSdk.kt`, `OstpVpnService.kt`).

- **Изолированная среда выполнения**: `ostp-jni` поднимает и владеет собственной многопоточной средой выполнения Tokio внутри процесса хоста, так что сетевой ввод-вывод туннеля никогда не блокирует UI-поток Android.
- **Мост телеметрии**: метрики и логи опрашиваются через границу JNI обычными безопасными для памяти геттерами, а не push-каналом — это держит поверхность FFI минимальной.

## Десктопный GUI
`ostp-gui` — десктопное приложение на Tauri v2 (сегодня ориентировано на Windows), которое управляет тем же клиентским движком через собственный слой-мост, предоставляя режимы системного прокси и TUN, импорт share-ссылок и управление исключениями. См. [страницу GUI-клиента в вики](https://github.com/ospab/ostp/wiki/GUI-Client).

### Разделение привилегий для TUN
Создание TUN-адаптера требует повышенных прав; запускать весь GUI с повышением нежелательно. Вместо этого настройка TUN делегируется `ostp-tun-helper` — небольшому отдельному процессу, который GUI запускает и с которым общается по локальному командному каналу (старт/стоп с конфигурацией + токеном авторизации) — с повышенными правами нужно запускать только этот хелпер, а не сам GUI. Собственно код создания адаптера (Windows/Wintun, Linux, macOS) лежит в общем крейте `ostp-tun`, используемом и хелпером, и нативным TUN-путём самого CLI (см. [`client.md`](client.md)).

## Системные интерфейсы
На десктопе за интеграцию с хостом отвечают платформо-специфичные модули:
- **Системный прокси Windows** (`sysproxy.rs`): записывает/восстанавливает значения прокси в реестре WinINet для проксирования браузеров без дополнительной настройки.
- **TUN-адаптеры** (`ostp-tun`): Wintun на Windows, нативные TUN-устройства на Linux/macOS; пользовательский стек `netstack-smoltcp` восстанавливает TCP/UDP-потоки из сырых IP-пакетов, которые доставляет адаптер.
- **Исключения по процессу** (Windows): сопоставляет локальное TCP-соединение с владеющим им процессом через `GetExtendedTcpTable`, так что правила обхода по процессу (§[`client.md`](client.md)) можно применять без драйвера ядра.
